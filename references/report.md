# 标准输出

面向用户的输出用中文交付：判定词、条目名、小节标题与固定声明全部中文优先，
检查 ID 与脚本原始代码（如 `not_assessed`、`canonical.placeholder.candidate`）
仅作括号内追溯后缀；`not_assessed` 在正文中显示为「未评估」，英文原码只保留
在候选观察的原始引用与落盘文件中。事实缺失时标记未评估，不推断为通过。

对人类读者，用平实语言说清结论、相关限制和下一步行动，同时保留检查 ID 以便
追溯。保留任何约定好的机器可读 schema。证据与前后对比摘录中脱敏凭据和私人
样例值；保留文件/节位置。

以下逐项分类、覆盖计数和渲染约束仅用于「静态合规报告」；复盘使用本文末尾的
简短「复盘改进报告」，不因一次复盘就要求完整审计。其他阶段按各自模板交付。

静态报告默认以 Markdown 正文文本交付；JSON 按[统一报告契约](report-json.md)交付。
两种格式使用同一完整结果，支持 concise/full；简短只省略通过项解释。
静态报告，排版清晰可读，重点前置：结论之后依次输出必修项、建议项、
不适用、未评估，通过项最后压缩为一块连续列举（中文名，ID 作括号后缀），默认
full 附通过项依据，concise 省略这部分解释。非通过项每条给出一句话证据并标注负责方
（按实际证据区分脚本事实与语义推断），判定词前置到行首，通过块以「通过 N 项」作块首。
**全部 23 个检查项必须逐条可数——包括判定为不适用和未评估的项**，「检查项
归类 N/N」按注册 ID 去重计数，基础分母为 23，Codex 配置增加 C01–C04，分母为 27；任何一项都不得在正文中省略。条目以
检查方面的自然语言命名（如「引用可达性」「触发与非触发」）。不使用 Markdown
表格，表格形态仅用于落盘文件。只有用户明确要求可视化时才渲染富呈现卡片，且
以文本版为完整契约、卡片仅为辅助快照。必修与建议在「待办」区汇总，无待修项时
一行带过。

颜色只标记偏离常态的信号：通过项不染色，必修红、建议黄；不适用与未评估用灰色
弱化。纯文本环境降级为「【通过】【必修】【建议】【不适用】【未评估】」前缀
标记。不使用 emoji 或装饰性颜色。

### 渲染形态（视觉一致性）

同一份报告内、以及跨报告之间，渲染形态必须逐条一致：

- **条目符号**：非通过项用无序列表（`-`）逐条列出；通过块用连续列举（顿号或
  `·` 分隔，单段不换行）；禁止混用有序编号与无序列表。
- **字段冒号**：字段名后统一中文全角冒号「：」，模板代码块已按此书写，照抄即一致
  （代码块、路径、JSON 内容保留原样字符）。
- **粗体使用**：仅两处——结论行的判词、必修项条目首的检查名；其余不加粗。
- **空值写法**：无发现字段统一写「无」，不写「—」「N/A」「暂无」。
- **条目内部结构**：非通过项固定为「检查名（ID）：一句话证据。怎么改：动作。」，
  三段顺序不换，句号收尾。
- **章节标题**：报告以正文文本交付，字段名不加 Markdown 标题符号（#）；报告名
  作为唯一标题行加粗。

默认只做一个完整的 `SKILL.md`。拆分资源必须有具名的条件性或重内容消费者。

## 静态合规报告

每次创建自检和现有 Skill 完整检查之后使用。字段按下方顺序输出；结论行自带覆盖
计数（视线起点即知查了多全），结论之后紧跟非通过项，通过块收尾。判词统一用
「静态」系（静态合规／静态不合规），与报告名一致，不使用「形式」一词。

```text
结论：判词——N 项全分类（x 通过 · y 必修 · z 建议 · u 不适用 · v 未评估）
     （判词为「无法判定」时紧跟原因「必需项证据不足，见未评估」；
       未全分类时用 N/23 暴露未分类数）
检查对象：<目标路径>
读取范围：应读文件已全读 | <仅列应读未读的文件及原因>
必修项（不修=静态不合规）：无 | <问题（ID）：哪里出了问题、对用户的影响。怎么改：动作。>
建议项（不影响合格判定）：无 | <问题（ID）：哪里出了问题、影响。怎么改：动作。>
不适用：无 | <检查方面（ID）与原因>
未评估：无 | <检查方面（ID）：为什么没查成>
通过 N 项：<中文名>（ID）· <中文名>（ID）· ……
变更证据：<仅复检报告：改了哪些文件、每处改前改后>
运行行为：未评估，超出 SCK 范围
下一步行动：<一个最小的有用动作>
```

字段分区（顺序即此分区）：审计头（结论、检查对象、读取范围）——先声明查谁、
读了什么、结论是什么；判定区（必修、建议）——用户需要修的和可以缓的；其余
分类（不适用、未评估）；收尾（通过块、变更证据、运行行为、下一步行动）。

面向用户语言（硬规则）：报告的读者是 skill 的使用者，不是 SCK 的开发者。

- 条目写「问题—影响—怎么改」，不写检查过程。技术术语首次出现必须跟平实
  释义：如「孤立资源（正文中没有指向它的链接）」「软链接（指向别处的快捷
  方式，可能绕出 skill 目录）」「frontmatter（文件开头的三横线之间的元信息）」。
- 脚本代码不直接代替问题解释；证据就地并入条目。为追溯保留的原始观察可在
  单独的处置段呈现，JSON 保留原始对象；严禁输出敏感值。
- 证据位置用「文件＋位置」的自然表述（如「README 第 10 行」「文件结构表」），
  不用内部字段名或 JSON 路径。
- 判词词表：静态合规 | 静态合规但有建议 | 静态不合规 | 无法判定。模板即
  形态：字段名、冒号、空值写法、条目结构照抄上方代码块，不再另设渲染例外。
  「无法判定」意为检查已跑完、有必需项证据不足、整体结论下不了——不是
  「检查没跑成」；结论行必须紧跟原因，不许单独出现（旧称「无法完成检查」
  在 23 项全部分类完毕时仍出现，使用者易误读，已弃用）。

候选观察保留在统一结果的 observations，Markdown 用简短「脚本观察处置」披露；
引用复核与检查项归类不另建重复章节。处置证据就地并入必修/建议/未评估条目
（引用问题的结论由通过块的「引用可达（S06）· 资源组织（L09）」承载）；
候选未决或应读未读进入「未评估」，正常确认静默通过，不重复展示。

覆盖计数已在结论行披露。每个 ID 只计入一个汇总状态：先判适用性，完全不适用的
计为不适用；其余按「未评估 > 必修 > 建议 > 通过」归并，取首个存在的状态。
同一 ID 的不同发现仍须完整保留，重复展示的证据不重复计数。五类计数之和等于
已分类的唯一 ID 数 N；23 项均有处置时为 23，未全分类时使用 N/23，不虚填剩余项。
计数统计检查项的汇总状态，不是问题条数。通过块条目名用自然语言中文（如
「元信息有效」，不写 frontmatter）。
两个判定等级的自解释规则：23 个检查项按清单分为必需（required，不达标即
判静态不合规）与建议（advisory，有发现不影响合格）两级；报告字段名直接
内嵌该后果，「必需缺口」「提醒项」等旧称不再使用。

判词规则（按顺序应用；第一条命中的规则决定结论）：

- 适用必需项证据不足：`无法判定`。已确认的必需依赖缺失是必修项而非单纯
  未知，要与文件系统证据不可得或含义未决区分开。
- 否则，存在任一必修项：`静态不合规`。
- 全部必需项通过且存在建议项：`静态合规但有建议`。
- 全部适用项通过且无建议：`静态合规`。

「检查项归类」已并入结论行覆盖计数；分子是已给出处置的唯一检查 ID 数量，不是
发现数或通过数。
同一项的多条证据不增加分子。

执行者证据纪律（面向内部，不逐条出现在报告正文）：保留已证实的必修发现和
原始脚本观察（warning 与 `not_assessed`），处置时附上清单中对应项的上下文
证据；未解决的适用必需判断列入「未评估」（缺证据≠缺文件），不能冒充通过。
如只读复核已补足某项，内部记录「脚本未评估；上下文复核已补足」及证据，报告
中只呈现最终处置；不得把原始脚本结果改写为已通过。同一 ID 的已知缺口与未完成
部分可以并存，按上面的判词规则汇总。范围外的运行正确性只保留固定声明，不纳入
必需项未评估数量。上下文补足适用于可从原文复核的判断；缺失 YAML 解析器仍按
S02 处理，不能用猜测解析来替代；需要工具才能证明的事实，必须取得有效工具证据。

例如：S06 同时有已确认的缺失引用和无法完成复核的引用，其唯一汇总状态为未评估。
必修区仍保留缺失引用，注明「本 ID 计入未评估，已知缺口仍需修复」；未评估区说明
未查完的部分。若另 20 项通过、1 项不适用，计数为「20 通过 · 0 必修 · 0 建议 ·
1 不适用 · 1 未评估」，共 23 项；结论为「无法判定」。0 必修汇总项不表示没有
已知缺口，必修区的证据不能因此隐藏。

占位符采用清单 S05 的处置，引用候选采用 S06/S08/L09 的处置；处置结论进入报告
对应条目，原始代码与行号留在执行者工作记录中。

例如：缺失 PyYAML 且已确认缺策略文件时，结论为「无法判定」，报告正文写
「需要加载的规则文件不存在（怎么改：补建文件或移除引用）」，YAML 相关检查
列入未评估（原因：缺少解析工具）。不隐藏任何一方事实，也不降级必修级。

完成检查意味着报告已交付，不代表目标通过。静态合规不证明执行、功能、安全或
宿主验收。

## 修改确认单

仅用于 Check 流程，在现有 Skill 静态报告之后、任何编辑之前使用。Reflect 流程
使用下文的复盘改进报告及其授权规则，不要求先把经验问题归成静态检查 ID。

```text
所选 ID：
将变更的既有文件：
新建文件：无 | 路径
删除或重命名：无 | 精确路径与原因
最小编辑：
保留内容：
可能影响：
临时回滚：仅复制受影响的普通文件；成功后删除
用户决定：待定 | 已确认 | 已拒绝
```

`已确认` 只授权列出的 ID 和路径。新目标或更大范围的变更需要重新确认。拒绝或不
回答都保持目标不变。删除或重命名既有内容需要显式的路径级确认。

## 标准样张（静态合规报告·全通过形态）

以虚构的干净目标演示字段序、冒号、空值与用户语言；照抄本样张即视为符合渲染
形态，有发现的字段按样张条目风格填充：

```text
静态合规报告 — example-skill

结论：静态合规——23 项全分类（19 通过 · 4 不适用）

检查对象：~/.workbuddy/skills/example-skill/

读取范围：应读文件已全读

必修项（不修=静态不合规）：无

建议项（不影响合格判定）：无

不适用：占位符检查（S05）与结构交接（S09）——未启用 SCK 模板标记（正文独立一行的格式开关）；声明与实现一致（L11）——本 Skill 无自带可执行内容；指令不重复（L13）——虚构样例无并行维护的同义规则。

未评估：无

通过 19 项
目标可读（S01）· 元信息有效（S02）· 名称规范（S03）· 目录一致（S04）· 引用可达（S06）· 无软链接（S07）· 资源齐整（S08）· 目的明确（L01）· 触发边界（L02）· 输入行为（L03）· 流程可执行（L04）· 输出清晰（L05）· 权限有界（L06）· 失败诚实（L07）· 条件契约（L08）· 资源组织（L09）· 文档一致（L10）· README 自足（L12）· 凭据扫描未命中（S10）

变更证据：<仅复检报告出现：改了哪些文件、每处改前改后>

运行行为：未评估，超出 SCK 范围

下一步行动：无待办
```

有发现时的条目风格（用户语言三段：问题—影响—怎么改）：

```text
- 文档说法不一致（L10）：README 说 S2 已验证通过，SKILL.md 说 S2 已降级未通过，两处矛盾，看 README 的人会高估模型能力。怎么改：把 README 那行改成与 SKILL.md 一致。
- 资源没有入口（L09）：正文提到 22 个文件但都没有用链接指向它们，其中 3 个只给离线建模用、11 个是历史旧版本，混在一起分不清哪些在用。怎么改：在文件结构表里用真实链接分组标明用途，旧版本移出运行目录。
- README 说不清来龙去脉（L12）：README 重复了名字和文件清单，但没讲它替谁解决什么问题，也没说怎么开始用，新读者看完仍不知道能拿它做什么。怎么改：补上「这是什么/解决什么」和「怎么开始用」两段，边界可指向 SKILL.md 的触发说明。
```

## 复盘改进报告

仅用于 Reflect。默认在对话中简短交付，不落盘、不建立复盘历史。未改动时说明
无需修改、证据不足或等待决定的原因；有修改时明确「已修改」与「效果已验证」
是不同结论。只读复盘不必附静态合规报告，也不展示全部 23 项或整体合规判词。

```text
结论：<无需修改／需补充证据／建议修改／已修改，效果待验证／未完成，具体原因>
对象与证据：<目标；本次预期与实际偏差；最小证据位置和版本关联，未知则说明>
归因与改进：<事实、原因或待验证解释；具体文件和修改；保留行为与影响>
授权：<仅复盘未授权写入／用户已授权此范围的优化／尚待决定的具体事项>
复查与限制：<实际检查范围与结果、未解决问题；未执行目标 Skill>
下一次观察：<修改后最小可观察结果；无需修改时可省略>
```

修改前呈现具体方案和授权状态；当前授权已覆盖的常规改动无需再询问。修改后
只更新实际变更、复查结果和剩余问题，不重复整份提案。失败时列出保留/恢复的
状态及必要的临时路径，不称已完成。多个问题分条呈现，避免堆叠固定字段。

复查没有覆盖的项目不冒充通过；已存在的独立缺口仍披露，不借复盘扩大修复范围。
有修改时明确写出「未执行目标 Skill；修改效果待后续使用验证」。如果用户后来提供了与
修订版匹配的使用证据，说明该次观察结果、来源与限制，不能把旧运行记录当新版本
验证，也不能推断所有场景均已有效。若另行请求完整静态检查，使用独立静态报告。

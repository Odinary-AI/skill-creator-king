# 标准输出

面向用户的输出用中文交付：判定词、条目名、小节标题与固定声明全部中文优先，
检查 ID 在分类条目中作括号内追溯后缀；脚本观察处置段可保留 ID 和原始代码
（如 `not_assessed`、`canonical.placeholder.candidate`）。`not_assessed` 在分类正文
显示为「未评估」，英文原码只保留在原始观察与 JSON 中。事实缺失时标记未评估，
不推断为通过。

对人类读者，用平实语言说清结论、相关限制和接下来怎么做，同时保留检查 ID 以便
追溯。保留任何约定好的机器可读 schema。证据与前后对比摘录中脱敏凭据和私人
样例值；保留文件/节位置。

以下逐项分类、覆盖计数和渲染约束仅用于「静态合规报告」；复盘使用本文末尾的
简短「复盘改进报告」，不因一次复盘就要求完整审计。其他阶段按各自模板交付。

静态报告默认以 Markdown 正文文本交付；JSON 按[统一报告契约](report-json.md)交付。
本文维护报告的语义和呈现要求，[渲染器](../scripts/render_report.py)实现这些要求，
下方标准样张从固定输入生成，不能另行手写维护一种形态。模板字段与渲染器输出必须
一一对应，由测试钉住；只改其中一份视为未完成。
两种格式使用同一完整结果，支持 concise/full；简短只省略通过项解释。

全部 24 个检查项必须逐条可数，基础分母为 24；Codex 增加 C01–C02，分母为 26。
结论行披露总数与分项计数，逐条归类列在审计明细的通过块中。
每个所选配置 ID 恰好出现一次分类，证据不足填「未评估」，不能省略 ID 或虚填通过。
未完成检查的运行错误按 JSON 契约返回，不生成部分合规报告。

### 渲染形态

- 顺序：报告名、检查对象、结论、必修项、建议项、不适用、未评估、限制、实际运行、
  待你决定、接下来怎么做；其后是纯文本分隔行「—— 以下为审计明细，供维护者追溯 ——」，
  再输出读取范围、通过块、通过项依据、脚本观察处置、变更证据。
- 前两行回答「查了谁、要不要动」，收尾回答「由你定什么、然后怎么做」；中间只放
  判定所需内容，其余全部进审计明细。
- C01–C02 是目标自带 `agents/openai.yaml` 时启用的补充检查，与本机运行宿主无关；
  对象行只写项数（如「26 项」），限制里注明这两项的触发来源。不把补充项写成宿主
  的名字，也不因此称目标“只适用于 Codex”。
- 不使用加粗、Markdown 章节标题、表格、颜色或装饰符号；分隔行是唯一允许的分区
  标记。字段冒号统一中文全角「：」。
- 结论句由判词映射成固定文本，不自由书写：静态合规「没有必须改的书面缺口」；
  静态合规但有建议「没有必须改的书面缺口，另有可缓改项」；静态不合规「有必须改的
  书面缺口」；无法判定「有一项必需检查没判成，先别下结论」。结论行写作
  「结论：<映射句>——<判词>（<24|26> 项：分项计数）」，映射句与判词不得互相矛盾。
- 必修与建议用无序列表，写「检查名（ID；脚本事实或语义推断）：位置与证据、影响。
  怎么改：动作；本次未改动。」；纯检查且无变更证据时必须带「本次未改动」，说明
  动作没有被执行。不适用只说明原因，未评估说明缺失证据及影响，不要求为它们
  编造修改动作。
- 判定字段（必修、建议、不适用、未评估、限制、实际运行、待你决定、接下来怎么做）
  始终输出，无内容写「无」；审计字段（通过项依据、脚本观察处置、变更证据）无内容
  则省略。
- 通过块按注册 ID 顺序连续列举中文名，ID 作括号后缀，位于审计明细内；concise 省略
  通过项依据，full 按相同理由分组展示依据。
- 未评估的原因以「工具侧：」或「对象侧：」开头，说明这条未知来自检查工具还是目标
  本身。工具规则不适用不算未评估。
- 待你决定只收一类事项：SCK 判不了、只有目标所有者能拍板、且答案可能改变判词。
  每项四段：检查名（ID）、疑问句、两种取值各自的后果、不回答时的默认。最多 3 条；
  写不出两种后果的一律回未评估；要不要改、要不要授权不在其中。
- 接下来怎么做写 1–3 条，只写顺序、取舍和回来找 SCK 的时机，不复述必修/建议的
  动作细节，不写检查 ID；无动作时写一句什么时候需要再查。
- 脚本观察处置按检查项合并：同类观察注明条数、处置与代表路径，逐条明细留在 JSON。

## 需求确认单

在起草新 Skill 之前呈现，并等待用户确认。

```text
目标：
目标平台与配置：Codex（codex）| Claude Code（generic）
目标父目录：<用户确认的绝对路径>
预期用户：
成功结果：
正例触发：
非触发场景：
输入与前提：
输出：
权限与副作用：
失败行为：
约束：
假设：
研究来源及影响：无 | 来源与采纳结论
待决问题：无 | 未解决的问题
可以创建：是 | 否
```

`可以创建：是` 要求所有方向性事实均已解决，或已被用户明确接受。

## 创建蓝图

在需求确认单获批之后、写文件之前呈现。

```text
Skill 名称：
最终目标路径：<确认的父目录内、尚不存在的新目录>
核心职责：
主流程与关键判断：<主要步骤；存在实质方法选择时，写明条件和对应动作>
强制方式：<脚本 / 测试 / 宿主检查 | 仅文字及理由>
完成证据：<可观察检查 | 无（低风险，原因）>
计划文件：
资源拆分理由：
明确排除项：
```

默认只做一个完整的 `SKILL.md`。拆分资源必须有具名的条件性或重内容消费者。
主流程与关键判断由创建 AI 提炼填写；没有实质分支时只写主要步骤，不新增用户问卷、
单独报告或审批。提炼与澄清回返遵循[创建指南](create.md#creation-blueprint)。

完成证据记录这个 Skill 是否需要自检、以什么形式自检；没有任务需要时写「无」和
低风险理由，纯响应不自动等于低风险。判断规则见
[创建指南](create.md#completion-evidence-by-task-shape)。

## 交付前回顾

在静态自检与修正之后、交付之前输出。它复用需求确认单和创建蓝图，不新增检查项、
ID、问卷或审批门；静态合规报告仍是唯一的合规判词。

```text
需求回溯：<关键要求/蓝图决策 → 草稿落点；未落实或明确排除的项及原因>
冷读发现：<问题（文件与位置）→ 已修 | 保留 | 待你定；无>
修正复读：<静态自检或本阶段改过的段落 → 无新增矛盾；无改动则写「无」>
遗留与限制：<需你决定或静态阶段无法确认的事项；无>
```

回溯至少覆盖需求确认单的关键要求和蓝图决策，包括「完成证据」这一行。简单 Skill
可以只写一两行；不要为凑格式编造发现。遗留项不另立清单：需要用户拍板的进入静态
报告的「待你决定」，无法确认的进入「限制」；回顾发现若对应既有检查项，归到该 ID，
不重复计数。阶段输出只做摘要，完整处置进入报告对应字段；标「待你定」的冷读项必须
在「遗留与限制」写出具体决策问题，只写标签不算交代。不输出「可交付」之类发布判词，
也不用它替代静态合规报告的结论。

## 静态合规报告

每次创建自检和现有 Skill 完整检查之后使用。字段按下方顺序输出；结论行自带总数
与分项计数，非通过项在前，通过块和条件性证据收在审计明细里。判词统一用
「静态」系（静态合规／静态不合规），与报告名一致，不使用「形式」一词。

```text
检查对象：<目标路径>（<只读检查|创建后自检> · <24|26> 项）
结论：<映射句>——<判词>（<24|26> 项：x 通过 · y 必修 · z 建议 · u 不适用 · v 未评估）
必修项（不修=静态不合规）：无 | <问题（ID）：哪里出了问题、对用户的影响。怎么改：动作；本次未改动。>
建议项（不影响合格判定）：无 | <问题（ID）：哪里出了问题、影响。怎么改：动作；本次未改动。>
不适用：无 | <检查方面（ID）与原因>
未评估：无 | <检查方面（ID）：<工具侧|对象侧>——为什么没查成、所需证据>
限制：无 | <实际限制>
实际运行：未评估（SCK 只做静态检查）
待你决定：无 | <检查项（ID）：<疑问句>；<选 A 的后果>；<选 B 的后果>；<不回答时的默认>。>
接下来怎么做：<1–3 条：顺序、取舍、回来找 SCK 的时机；不复述动作细节，不写 ID>
—— 以下为审计明细，供维护者追溯 ——
读取范围：实际读取：<相对路径列表 | 无>；应读未读：<文件与原因 | 无>
通过 N 项：<中文名>（ID）· <中文名>（ID）· ……
通过项依据：<仅 full 且有通过项时输出>
脚本观察处置：<同类观察按检查项合并，注明条数与代表路径；逐条见 JSON>
变更证据：<仅复检报告：改了哪些文件、每处改前改后>
```

字段分区：正文区（检查对象、结论、必修项、建议项、不适用、未评估、限制、实际运行、
待你决定、接下来怎么做）——先交代查谁、结论是什么，再列必须修的和可以缓的，然后
是没查成的、限制、边界声明，最后是待你拍板的假设和下一步；审计明细区（读取范围、
通过块、通过项依据、脚本观察处置、变更证据）——供维护者追溯，不构成第二套结论。

面向用户语言（硬规则）：报告的读者是 skill 的使用者，不是 SCK 的开发者。
若发生先读后扫，限制段必须写明偏差和扫描后的重读范围；该偏差不计入必修或建议，
但扫描前读到的内容不能作为证据。

- 条目写「问题—影响—怎么改」，不写检查过程。技术术语首次出现必须跟平实
  释义：如「孤立资源（正文中没有指向它的链接）」「软链接（指向别处的快捷
  方式，可能绕出 skill 目录）」「frontmatter（文件开头的三横线之间的元信息）」。
- 脚本代码不直接代替问题解释；证据就地并入条目。为追溯保留的原始观察可在
  单独的处置段呈现，JSON 保留原始对象；严禁输出敏感值。
- 证据位置用「文件＋位置」的自然表述（如「README 第 10 行」「文件结构表」），
  不用内部字段名或 JSON 路径。
- 判词词表：静态合规 | 静态合规但有建议 | 静态不合规 | 无法判定。字段名、
  冒号、空值写法、条目结构按上方约定，精确输出见生成样张。
  「无法判定」意为检查已跑完、有必需项证据不足、整体结论下不了——不是
  「检查没跑成」；结论句固定为「有一项必需检查没判成，先别下结论」，具体原因
  写在未评估段并标明来源（旧称「无法完成检查」在 24 项全部分类完毕时仍出现，
  使用者易误读，已弃用）。

候选观察保留在统一结果的 observations，Markdown 用简短「脚本观察处置」披露；
引用复核与检查项归类不另建重复章节。处置证据就地并入必修/建议/未评估条目
（引用问题的结论由通过块的「引用可达（S06）· 资源组织（L09）」承载）；
未决评估或应读未读进入「未评估」；S10 未决候选按清单的发布/非发布规则处置。
确认后的最终结论进入对应条目，原始观察仅在处置段保留，不增加覆盖计数。

覆盖计数已在结论行披露。每个 ID 只计入一个汇总状态：先判适用性，完全不适用的
计为不适用；其余按「未评估 > 必修 > 建议 > 通过」归并，取首个存在的状态。
同一 ID 的不同发现仍须完整保留，重复展示的证据不重复计数。五类计数之和等于
已分类的唯一 ID 数 N；24 项均有处置时为 24，Codex 为 26，不虚填剩余项。
计数统计检查项的汇总状态，不是问题条数。通过块条目名用自然语言中文（如
「元信息有效」，不写 frontmatter）。
两个判定等级的自解释规则：24 个检查项按清单分为必需（required，不达标即
判静态不合规）与建议（advisory，有发现不影响合格）两级；报告字段名直接
内嵌该后果，「必需缺口」「提醒项」等旧称不再使用。

判词规则（按顺序应用；第一条命中的规则决定结论）：

- 适用必需项证据不足：`无法判定`。已确认的必需依赖缺失是必修项而非单纯
  未知，要与文件系统证据不可得或含义未决区分开。「未评估」只承载缺证据：
  读不到文件、缺解析器、扫描未覆盖；工具规则不适用不算未评估。
- 否则，存在任一必修项：`静态不合规`。
- 全部必需项通过且存在建议项：`静态合规但有建议`。
- 全部适用必需项通过且无建议：`静态合规`。建议项未评估不阻断此判词，
  但仍在覆盖计数和未评估区披露，不能计为通过。

适用性歧义（只有目标所有者能确认的事实，如宿主命名契约）不进未评估，按「待你
决定」列出该假设、两种取值各自的后果和不回答时的默认；假设被推翻时按新事实
重判，不追溯改写原始观察。

「检查项归类」已并入结论行覆盖计数；分子是已给出处置的唯一检查 ID 数量，不是
发现数或通过数。
同一项的多条证据不增加分子。

执行者证据纪律（面向内部，不逐条出现在报告正文）：保留已证实的必修发现和
原始脚本观察（warning 与 `not_assessed`），处置时附上清单中对应项的上下文
证据；未解决的适用必需判断列入「未评估」（缺证据≠缺文件），不能冒充通过。
如只读复核已补足某项，内部记录「脚本未评估；上下文复核已补足」及证据，报告
中只呈现最终处置；不得把原始脚本结果改写为已通过。同一 ID 的已知缺口与未完成
部分可以并存，按上面的判词规则汇总。范围外的运行正确性只保留固定声明，不纳入
必需项未评估数量。上下文补足适用于可从原文复核的判断；缺失 YAML 解析器仍按
S02 处理，不能用猜测解析来替代；需要工具才能证明的事实，必须取得有效工具证据。

例如：S06 同时有已确认的缺失引用和无法完成复核的引用，其唯一汇总状态为未评估。
必修区仍保留缺失引用，注明「本 ID 计入未评估，已知缺口仍需修复」；未评估区说明
未查完的部分。若另 22 项通过、1 项不适用，计数为「22 通过 · 0 必修 · 0 建议 ·
1 不适用 · 1 未评估」，共 24 项；结论为「无法判定」。0 必修汇总项不表示没有
已知缺口，必修区的证据不能因此隐藏。

占位符采用清单 S05 的处置，引用候选采用 S06/S08/L09 的处置；处置结论进入报告
对应条目，原始代码与行号留在执行者工作记录中。

例如：缺失 PyYAML 且已确认缺策略文件时，结论为「无法判定」，报告正文写
「需要加载的规则文件不存在（怎么改：补建文件或移除引用）」，YAML 相关检查
列入未评估（原因：缺少解析工具）。不隐藏任何一方事实，也不降级必修级。

完成检查意味着报告已交付，不代表目标通过。静态合规不证明执行、功能、安全或
宿主验收。

## 修改确认单

仅用于 Check 流程，在现有 Skill 静态报告之后、任何编辑之前使用。Reflect 流程
使用下文的复盘改进报告及其授权规则，不要求先把经验问题归成静态检查 ID。

```text
所选 ID：
将变更的既有文件：
新建文件：无 | 路径
删除或重命名：无 | 精确路径与原因
最小编辑：
保留内容：
可能影响：
临时回滚：仅复制受影响的普通文件；写入成功即删除，后续复查不自动回滚
用户决定：待定 | 已确认 | 已拒绝
```

`已确认` 只授权列出的 ID 和路径。新目标或更大范围的变更需要重新确认。拒绝或不
回答都保持目标不变。删除或重命名既有内容需要显式的路径级确认。

## 标准样张（静态合规报告·无必修或建议）

以下为虚构目标的 concise 输出，由源码测试固定输入生成并逐字验证。
目标没有启用模板标记、不含可执行内容，也没有并行维护规则；对应五项不适用。

## 复盘改进报告

仅用于 Reflect。默认在对话中简短交付，不落盘、不建立复盘历史。未改动时说明
无需修改、证据不足或等待决定的原因；有修改时明确「已修改」与「效果已验证」
是不同结论。只读复盘不必附静态合规报告，也不展示全部 24 项或整体合规判词。

```text
结论：<无需修改／需补充证据／建议修改／已修改，效果待验证／未完成，具体原因>
对象与证据：<目标；本次预期与实际偏差；最小证据位置和版本关联，未知则说明>
归因与改进：<事实、原因或待验证解释；具体文件和修改；保留行为与影响>
授权：<仅复盘未授权写入／用户已授权此范围的优化／尚待决定的具体事项>
复查与限制：<实际检查范围与结果、未解决问题；未执行目标 Skill>
下一次观察：<修改后最小可观察结果；无需修改时可省略>
```

修改前呈现具体方案和授权状态；当前授权已覆盖的常规改动无需再询问。修改后
只更新实际变更、复查结果和剩余问题，不重复整份提案。失败时列出保留/恢复的
状态及必要的临时路径，不称已完成。多个问题分条呈现，避免堆叠固定字段。

复查没有覆盖的项目不冒充通过；已存在的独立缺口仍披露，不借复盘扩大修复范围。
有修改时明确写出「未执行目标 Skill；修改效果待后续使用验证」。如果用户后来提供了与
修订版匹配的使用证据，说明该次观察结果、来源与限制，不能把旧运行记录当新版本
验证，也不能推断所有场景均已有效。若另行请求完整静态检查，使用独立静态报告。
